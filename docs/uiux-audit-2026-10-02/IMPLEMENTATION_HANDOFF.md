## A01：下書きとURL初期値の競合を解消する

**対象**：`src/pages/PostReviewPage.jsx` 651行付近（URL初期化）、683行付近（下書き復元）、515行付近（確認表示）。関連：`src/contexts/DataContext.jsx` の店舗一覧取得。

**発生条件・原因**：人物Bの公開待ち下書きがある状態で、人物Aの投稿URLを新しいタブなどから開く。下書き復元後に店舗一覧が届くと、`shops` を依存に持つURL初期化effectが再実行される。その処理は `shopId`・`therapistId` だけをAへ変え、Bの人物名・評価・本文を残す。確認表示は入力済みの人物名を優先するため、IDの不一致も見抜きにくい。

模擬実行では、`shopB / idB / nameB / 本文B / step4` が、店舗一覧到着後に `shopA / idA / nameB / 本文B / step2` へ変わった。

**修正方法**：

1. URL初期値と下書きの読み込みを、一つの初期化処理で調停する。別々のeffectでフォームへ書き込まない。
2. 対象が違う下書きには「保存した下書きを再開」「開いた人物へ新しく書く」を提示する。選択前に下書きやフォームを上書きしない。
3. 店舗ID・人物ID・人物名を一組として初期化する。店舗データの到着や再取得では、確定した投稿先と本文を変更しない。
4. 同じ画面コンポーネント内でURLが変わる場合も扱う。単に「一度実行済みref」を置いて、新しい投稿URLを永久に無視する修正にはしない。
5. 送信前にも選択対象の整合性を確認し、不一致なら編集を案内する。本文を別人物へ自動転用しない。

**完了条件**：通常／公開待ち下書き、同じ／別の投稿先、店舗一覧の先着／後着、直接表示／内部遷移で検査。画面の店舗・人物名・本文と、保存予定payloadの `shop_id`・`therapist_id`・`therapist_name` が一致する。テスト口コミを本番へ作らず、まずローカルで確認する。

## A02：履歴・お気に入りの保存失敗で閲覧を止めない

**対象**：`src/hooks/useRecentlyViewed.js` 49〜69行付近、`src/pages/ThreadDetailPage.jsx` 214〜229行付近、`src/context/AppContext.tsx` 48〜70行付近。波及先：`src/components/ErrorBoundary.jsx`、`pages/_app.jsx`。

**発生条件・原因**：端末の保存容量不足や保存拒否で `localStorage.setItem` が例外を返す。人物ページは表示時に履歴へ追加するが、その書き込みに例外処理がない。Reactのstate更新関数内で書いているため、単なる履歴保存失敗が画面のエラーへ波及する経路がある。お気に入り更新、履歴削除にも同種の未捕捉処理がある。

現行 `addToHistory` に容量不足を返す保存領域を与えた模擬実行で、`QuotaExceededError` が呼び出し元へ伝播した。全画面のエラー表示への波及はコード確認であり、本番再現はしていない。

**修正方法**：

1. 読み込み・書き込み・削除を、成功／失敗を返すストレージ処理で包む。例外をReactの描画まで伝播させない。
2. state更新関数は純粋な計算にし、永続化を分離する。effectへ移す場合は、初期読み込み前の空配列で保存済みデータを上書きしないよう初期化状態を持つ。
3. 履歴を永続保存できなくても人物ページと口コミ本文は表示する。お気に入りは、保存失敗を短く案内し、永続保存に成功したような表示にしない。
4. ユーザー別お気に入りのキーと既存データを維持し、全保存領域の削除で回避しない。

**完了条件**：容量不足、保存拒否、削除拒否、壊れた保存JSONを模擬しても閲覧が続く。正常時の追加・重複除外・最大10件・再読込復元・ユーザー別お気に入りが維持される。

## A03：下書き保存失敗中のサイト内移動も保護する

**対象**：`src/features/reviews/hooks/useReviewForm.js` 43〜53行、`src/pages/PostReviewPage.jsx` 897行付近・1022行付近、`src/components/Header.jsx` 82行付近、`src/compat/router`。

**発生条件・原因**：下書き保存に失敗した後、ヘッダーロゴなどの内部リンクで移動する。現在は投稿ボタンからログインへ移動する経路だけ保存失敗で止まる。`beforeunload` はNext.jsのページ内遷移では発火しないため、保存されていない入力を残して画面が破棄される。

**修正方法**：

1. 「入力がある」だけでなく、最後に保存できた内容と現在の内容を比較して未保存状態を判定する。
2. ヘッダー・キャンセル・内部リンク・履歴の戻る等、投稿画面を破棄する経路に共通の離脱保護を適用する。既存ルーターとの整合を確認する。
3. 未保存なら再保存し、失敗時は「画面に残る」「本文をコピー」「保存せず移動」を選べるようにする。本人が選ぶ前に移動を完了させない。
4. 画面終了／再読み込みの `beforeunload` も維持する。コピー失敗時の全文選択欄を再利用する。

**完了条件**：保存失敗後のロゴ、内部リンク、キャンセル、戻る、再読み込みで入力を黙って失わない。保存成功時や投稿完了後には不要な確認を出さない。保存直前の1秒間に移動するケースも検査する。

## A04：マイページにも閲覧権の状態分離を適用する

**対象**：`src/pages/MyPage.jsx` 18〜31行、41〜49行、80行、104行付近。再利用先：`src/hooks/useViewingCredits.js`。

**発生条件・原因**：ログイン後の権利取得が遅延・失敗すると、初期値／失敗値の `null` を「閲覧権なし」、投稿件数を「0件」と表示する。期限を計算する `useMemo` には時刻による更新もなく、開いたまま期限を過ぎても表示が残る。前回の共通フック導入はこの画面には及んでいない。

**修正方法**：閲覧権の判定を `useViewingCredits` に統一し、「確認中」「確認失敗＋再試行」「期限切れ」「有効」を分ける。必要な `expiresAt` をフックから返す。投稿件数は独立した取得状態を持たせ、未取得・取得失敗は「—」等とし0に変換しない。実際の権利判定は `expires_at` を使い続ける。ユーザー切替時に前の情報を表示しない。

**完了条件**：遅延→成功、503→再試行、期限到達、ユーザー切替を確認。口コミ本文側の閲覧状態と矛盾しない。無料会員・有効な閲覧権・プレミアム等の既存区分を維持する。

## A05：口コミ一覧の初回取得失敗を「0件」と表示しない

**対象**：`pages/popular-reviews.jsx` 64行付近、`src/pages/PopularReviewsPage.jsx` 53行・171行・388行付近。

**発生条件・原因**：口コミ一覧のサーバー取得が失敗すると、HTTP503・no-storeにはなるが、propsが `initialReviews: []` のため画面は正常0件と判断する。初回クライアント取得も省略し、「口コミがまだありません」と表示して再試行を出さない。ホーム修正とは別経路。

**修正方法**：

1. SSRから `initialLoadError` または明示的な取得状態を渡す。空配列だけで成功／失敗を判断しない。
2. 口コミの必須取得が失敗したら503・no-store・Retry-Afterを維持し、「読み込めませんでした」＋再試行を表示する。
3. 店舗名・写真等の補助情報だけ取得に失敗した場合、取得済み口コミを残す。補助情報なしを退店・削除などと断定しない。
4. 正常に0件を確認した場合だけ空状態と投稿案内を表示する。SSR後の内部遷移でも同じ契約にする。

**完了条件**：口コミ取得失敗、店舗情報失敗、人物情報失敗、正常0件、再試行成功を別々に検査。エラーを「最初の口コミを書く」という案内に置き換えない。

## A06：口コミ一覧の並び替えと追加取得の競合を止める

**対象**：`src/pages/PopularReviewsPage.jsx` 128〜191行付近、228行付近。

**発生条件・原因**：「評価順」→「新着順」と切り替え、評価順の古い応答が後から届くと、新着タブのまま評価順が表示される。古い追加取得も新しい並びへ混ざり得る。また、切替先の取得が失敗しても、既存口コミがある場合はエラー表示条件から外れ、旧一覧を新タブの結果に見せる。

**修正方法**：

1. 並び替えごとにリクエスト世代を持つ。成功・失敗・`finally` のすべてで、現在の世代でない応答を無視する。通信中止だけに頼らない。
2. 追加取得を開始時点の世代・並び順へ所属させる。切替前の追加取得で、新一覧のカード・offset・hasMoreを更新しない。
3. 表示済みの並びと選択中の並びを区別するか、取得成功までは旧タブを維持する。失敗時は既存口コミがあってもエラーと再試行を出す。
4. 前回修正した「成功後にだけoffsetを進める」「同じoffsetで再試行する」「IDで重複排除する」は維持する。

**完了条件**：評価順→新着順の応答逆転、追加取得中の並び替え、切替失敗、再試行、アンマウントを検査。タブ・カード順・offsetが一致し、古い完了処理で現在のローディングを解除しない。

## A07：お気に入りの保存件数と取得状態を分ける

**対象**：`src/pages/FavoritesPage.jsx` 28〜72行付近、238行付近。

**発生条件・原因**：保存した人物IDがあっても、人物キャッシュが空で取得が失敗すると、`data || []` から空mapを作り、「推しメンがまだいません」と表示する。読込中も同じ誤表示になり、再試行がない。保存データ自体の削除ではない。

**修正方法**：保存IDの件数、店舗索引の準備、人物の取得中／成功／失敗を分離する。取得失敗には再試行を出し、表示済みデータは残す。実際に保存IDが0件の場合だけ未登録案内を出す。正常取得しても見つからないIDは「情報を取得できない保存項目」として扱い、通信失敗を理由に保存IDを自動削除しない。店舗タブにも同じ状態の考え方を適用する。

**完了条件**：保存1件・キャッシュ空・503→エラー→再試行200で復元、正常0件、店舗索引の遅延、ユーザー切替を検査。タブ件数を一時的な取得失敗で0にしない。

## A08：店舗・ブランドの絞り込みも1024px境界で閉じる

**対象**：`src/pages/ShopDetailPage.jsx` 315〜320行、`src/components/TagFilterSidebar.jsx` 35〜50行、`src/pages/BrandPage.jsx` 171行・443行付近。参照：`src/pages/SearchPage.jsx` 271〜307行。

**本番再現**：[RELAX店舗ページ](https://www.mens-esthe-map.jp/shops/tokyo_minato_shinbashi_relax_tokyo)を768px幅で開き、「タグで絞り込む」を押す。そのまま1024pxへ広げると、`body` の `overflow` は `hidden` のまま、閉じるボタン・背景ボタン・開くボタンがすべて非表示になる。ページ高10,748px／画面高900pxでロックが残った。768pxへ戻して閉じると `visible` に復帰した。

**原因**：検索ページにある境界変更時の自動クローズが店舗ページにない。共有サイドバーは閉じる操作だけをPC幅で隠す。ブランドページも同じ部品を使うが、同じロック症状の本番再現までは確認していない。

**修正方法**：開閉・1024px境界判定・スクロールロック解除・Escape・フォーカス復帰を共通化し、店舗とブランドに適用する。1024px以上ではモバイル用 `inset`・`bottom` 等も解除する。PCの「左にタグ、右に人物一覧」と、タグ0件でも欄を表示する仕様は維持する。

**完了条件**：店舗とブランドで768→1024→768、390→1440、シート開閉、Escape、キーボードのフォーカスを確認。閉じた後や別ページへの移動後にもbodyのロックが残らない。

## A09：投稿画面の店舗候補をキーボードでも選べるようにする

**対象**：`src/pages/PostReviewPage.jsx` 171〜205行付近。

**本番確認**：`/post-review` の店舗検索に `RELAX` と入力し、「RELAX (リラックス) 東京都・新橋」候補をEnter、Spaceで操作した。候補にフォーカスが移っても選択されず、チェックマークも人物選択欄も現れなかった。口コミや店舗選択の保存は行っていない。

**原因**：候補ボタンに `onMouseDown` しかなく、キーボードで発生する `click` に選択処理がない。

**修正方法**：選択処理を `onClick` で実行し、候補を閉じる処理との競合は別に調整する。検索欄へ適切なlabelを結び付け、候補との関連・開閉状態・選択状態を支援技術へ伝える。矢印・Enter・Escapeも実装する場合は、コンボボックスとして一貫して操作できるようにする。

**完了条件**：マウス・タッチ・Tab→Enter・Tab→Spaceで同じ店舗を選べる。選択でフォームが勝手に送信されない。候補を閉じてもフォーカスを見失わない。

## A10：タグ横の数字の説明を人物数に合わせる

**対象**：`src/components/TagFilterSidebar.jsx` 80行、`src/pages/ShopDetailPage.jsx` 293行付近、`src/pages/BrandPage.jsx` 174行付近。

**原因**：説明は「数字は付いた口コミの件数」だが、集計は人物ごとのタグ集合を1回ずつ数えている。同じ人物へ同じタグが2口コミ付いても1。

**修正方法**：人物を絞り込む現在の集計を維持し、説明を「数字は、そのタグが付いたセラピストの人数です」に合わせる。口コミ件数へ変更すると意味が変わるため、この修正では集計を変えない。

**完了条件**：人物Aに同タグ2口コミ、人物Bに同タグ1口コミなら2人と読み取れる。店舗・ブランド両画面で同じ説明になる。
